# レビューの観点

上から順に、学習効果とほかの問題への波及が大きいもの。すべてを指摘する必要はない。プロジェクトに実際にあるものだけを拾う。

## 1. 動かない・壊れている

- コンパイルエラー
- 実際のバグ。再現手順（どのメニューをどの順に選ぶか）を書けるもの
- 例外で落ちる入力（範囲外の番号、数字以外の入力など）。初学者向けには、優先度を下げて1つにまとめる

## 2. 継承とポリモーフィズム

- is-a が成り立たない継承（「A は B の一種である」と言えるか）
- 親クラスが `instanceof` で子クラスを判定している（親が子に依存）
- 状態の変化を「別クラスのオブジェクトに作り直す」ことで表している
- インターフェースに、一部の実装しか使わないメソッドがある（`return null` だけの実装）
- インターフェースにないメソッドを、呼び出し側が具体クラス名で呼んでいる

## 3. 責務とクラス分け

- 1つのクラスが複数の種類の仕事をしている（変更する理由が複数ある）
- ある情報を持つべきクラスが別にある（例：料金はランクが持つ、日数は貸出が持つ）
- 現実の概念に対応するクラスが欠けている（例：貸出伝票）
- 同じ情報が2か所にあり、食い違う可能性がある（フラグとクラスの種類、コピーした値）

## 4. カプセル化

- getter が内部の可変リストをそのまま返し、外側で `add` や `remove` をしている
- `public` や不要な `protected` のフィールド
- 同じチェックが複数の場所に散らばっている

## 5. 入出力とロジックの分離

- 計算や状態変更のメソッドの中で `System.out` を使っている
- `Scanner(System.in)` が複数作られている、使われていない

## 5.5 Java の基本

- インスタンスごとに持つべき値やオブジェクトを `static` にしている
- オーバーライドのつもりで `@Override` を付け忘れ、引数の違いでオーバーロードになっている
- コンストラクタの同じ初期化の重複（`this(...)` で呼べる）、引数の値のチェックがない
- 文字列を `==` で比べている

## 6. 値の表し方

- 決まった数種類の値を `int` や `String` で表している（enum 候補）
- 配列の添字と意味の対応が暗黙の約束になっている
- 不正な値でオブジェクトが中途半端に作られる（コンストラクタで例外を投げていない）
- 意味が逆に読める boolean（`rented = true` が「借りられていない」など）

## 7. 命名とパッケージ

命名の問題があれば、優先度は低くても必ず1つのヒントにまとめて入れる。「今の名前・場所・何を表しているか・新しい名前の案」の表にし、案は最初の1〜2行だけ埋めて残りは「？」にする。

- 中身がわからない名前（`n`、`d`、`a`、`temp`、`data`、`flag` など。ループの `i`、`j` は問題にしない）
- 名前と中身・役割が合わない（`found` がメニューを続けるかのフラグ、`list` の中身が客、`value11` のような番号付きの名前、`setXxx` なのに加算している）
- 品詞の習慣（クラスは名詞、メソッドは動詞、boolean は `is`／`has`／`can`、定数は大文字のスネークケース）
- 大文字・小文字の習慣（クラスは大文字、パッケージ・メソッド・変数は小文字で始める）
- 同じものを別の名前で呼んでいる（同じ管理者を `manager`、`ai`、`man` と呼び分ける）
- パッケージ名とクラス名が同じ、置き場所がおかしいクラス
- ローマ字と英語の混在、タイポ
- ソース以外のもの（メモ用のクラス、`bin/` の `.class` が git 管理下にある）

## レベル

レベルで変えるのは「見る観点の範囲」と「ヒントの厚さ・口調」だけ。流れと `HINTS.md` の形式は共通。

- **初学者（既定）**：上の観点1〜7を見る。ヒントは問い・手順・骨組みまで丁寧に書き、できているところは具体的に認める。
- **中級**：観点1〜7に加えて、抽象クラスとインターフェースの使い分け、変わらないフィールドの `final`、実装クラス（`ArrayList` など）での変数宣言、ほぼ同じ処理のコピー、例外を `catch` して何もしない・`Exception` でまとめて受ける、`null` を返す・受け取る設計も見る。骨組みは要所だけにし、手順は短く、口調はやわらかいまま簡潔に。
- **上級**：観点1〜7は明らかな問題だけに絞り、設計原則（単一責任・開放閉鎖・依存性逆転など）、依存の向きと結合度、テストのしやすさ（内部での `new` の決め打ち、`static` への依存）、例外の設計、ジェネリクスや不変オブジェクトの活用、デザインパターンが自然に当てはまる箇所（無理に当てはめない）を中心に見る。ヒントは指摘と問いを中心に簡潔に、骨組みは必要なときだけ、手順は1〜3ステップ。
