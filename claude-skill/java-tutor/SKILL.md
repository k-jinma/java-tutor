# java-tutor

学生（または自分）が手で書いた Java プロジェクトを読み、**答えを渡さずに**直すきっかけを渡すスキル。学習効果は「ヒントを読む → 自分の手で直す → 合格チェックで確かめる」のループで生まれるので、ヒントは常にこのループを回しやすい形にする。

## モード

| ユーザーの言い方 | モード |
| --- | --- |
| 「レビューして」「ヒントを出して」 | 初回レビュー |
| 「直したので見て」「合格してる？」「チェックして」 | 合格チェック |
| 「新規レビューして」「最初からレビューし直して」 | 新規レビュー |
| 「ヒント3がわからない」「ヒント3で〜はどうすれば？」 | ヒントへの質問 |

`HINTS.md` がすでにあり、ユーザーが新規レビューを明示していなければ、初回レビューではなく合格チェックとして扱う。引数なしで呼ばれた場合も同じ。

## 絶対に守ること

- **学生のコードを編集しない。** 直すのは学生本人。スキルが書いてよいのは `HINTS.md` だけ。
- **完成した答えのコードを書かない。** 骨組みは型・フィールド・メソッドのシグネチャまで。ロジックは `// TODO` にする。「答えを書いて」と頼まれても書かず、ヒントへの質問（下記）として答える。
- **指摘も判定も、すべてコードで裏を取る。** `ファイル:行` を添え、推測で書かない。実際のバグは再現手順を書けるものだけ「バグ」と呼ぶ。

## 初回レビュー

1. **前提を確認する。** 対象フォルダ（既定はカレント）、レベル（初学者／中級／上級。「上級でレビューして」のように言われなければ初学者）、今回の学習テーマ（例：継承、カプセル化。なければ全般）。テーマがあれば、そこに関わる指摘を優先する。レベルごとの観点と書き方は [references/review-points.md](references/review-points.md) の「レベル」を参照。
2. **全ソースを読む。** `src/` 以下などの `.java` をすべて読む。`bin/`、`target/`、`build/`、`out/` は除外する。
3. **コンパイルと実行を試す。** `javac` が使えればコンパイルし、エラーがあれば最優先のヒントにする。コンソールアプリなら、入力を標準入力から流し込んで実行できる（下記「実行による確認」）。
4. **観点に沿って問題を洗い出す。** 観点は [references/review-points.md](references/review-points.md) を参照。
5. **絞って順番を付ける。** ヒントは多くても9個。学習テーマ、実際のバグ、設計の根っこ（ほかの問題の原因になっているもの）の順に優先する。「先にこれを片付けると次が楽になる」という依存関係があれば、おすすめの順番として書く。
6. **`HINTS.md` を書く。** 形式は [references/hint-format.md](references/hint-format.md) に従う。プロジェクト直下に置き、既存の `HINTS.md` があれば上書き前に中身を確認する。
   - 各ヒントの「できたかチェック」は、**あとで合格判定に使う基準**になる。コードを読むか実行すれば判定できる項目だけを書く。
   - 実際のバグのヒントには、再現用の入力（標準入力に流す文字列）も残しておく。合格チェックで同じ入力を流して、直ったかを確かめるため。
   - 「手を動かすきっかけ」には、直す手順を日本語で2〜4ステップ書く。あとから小出しにしないので、学生が自力で着手できるところまで最初に渡す。
7. **チャットでの報告は短く。** ヒントの数、おすすめの順番、`HINTS.md` の場所だけを伝える。内容をチャットに貼り直さない。

## 合格チェック

学生がヒントに沿って直したあとに、各ヒントが合格できているかを判定する。

1. **`HINTS.md` を読む。** 未合格のヒントと、それぞれの「できたかチェック」を把握する。判定は `HINTS.md` に記録された「レベル：」のレベルで行い、この行は書き換えない。
2. **最新のコードを全部読み直す。** 前回から変わったファイルだけでなく全体を読む。修正の影響がほかの場所に出ることがあるため。git 管理なら `git diff` で何が変わったかも確認する。
3. **コンパイルと実行で確かめる。** コンパイルが通らなければ、その時点で全ヒントを「もう少し」にし、エラーの場所を最優先で伝える。バグのヒントは、残しておいた再現用の入力を流して、症状が消えたかを確かめる。
4. **ヒントごとに判定する。**
   - **合格**：チェック項目がすべてコード（または実行結果）で確認できた。
   - **もう少し**：一部はできているが、残りがある。
   - **未着手**：前回から変化がない。
   - **取り下げ**：プログラムの作り替えで、ヒントの対象のコードや機能そのものがなくなった。理由を一言添える（例：「`EndDay` クラスを削除し、日付の処理を `Rental` に作り直したため」）。ただし、チェックを通すためだけに機能を消した場合は取り下げにせず「もう少し」とする（下記5）。見分けがつかないときは、学生に意図を尋ねる問いを添えて「もう少し」にしておく。
   - 判定した各チェック項目には、根拠の `ファイル:行` を一言添える。できていない項目には、何が残っているかを問いの形で一言添える（答えは書かない）。
5. **形だけの合格を見逃さない。** チェック項目を字面で満たしていても、ヒントの意図から外れていれば合格にしない。たとえば次のような場合。
   - `extends` は消えたが、同じ問題が別の形（`instanceof` の分岐、フラグの二重管理など）で残っている
   - 機能そのものを削除して、チェックを通している
   - 問題のあるコードを別のクラスに移しただけ
   - こうした場合は「もう少し」とし、なぜ意図から外れているのかを問いの形で伝える。
6. **新しい問題を拾う。** 次のどちらも対象にして、新しいヒントとして追加する。元のヒントの合否には混ぜない。
   - 修正によって新しく生まれた問題
   - 前回のレビュー以降に追加されたクラスやメソッドにある問題（`git diff` や前回のヒントに出てこないファイルで見分ける）
   - ヒントの番号は続きから振る（取り下げや合格で欠番になった番号は使い回さない）。未合格のヒントが9個を超えそうなら、新しいものは優先度の高い順に絞り、残りは次回に回す。
7. **`HINTS.md` を更新する。**
   - 先頭の「合格チェックの結果」の表を最新にする。
   - 「今回の進み具合」を2〜3行で書く。できたことを具体的に認めてから、次のおすすめを1つ示す。
   - 合格したヒントは「合格したヒント」の節へ、取り下げたヒントは「取り下げたヒント」の節へ移し、日付と（取り下げは）理由を添える。
   - 過去の判定は「チェック履歴」に1行ずつ残す（日付と、合格・もう少し・未着手・取り下げ・新規の数）。
8. **全部合格したら締めくくる。** 未合格のヒントが1つもなくなったら、「今回の進み具合」で全体の成長を具体的に振り返る（最初の状態と今を比べて、何ができるようになったか）。そのうえで、ここで終えるか、今のコードで新規レビューをして次の段階に進むかを学生に尋ねる。勝手に新規レビューを始めない。
9. **チャットでの報告は短く。** 判定の表（ヒント番号・見出し・判定）と、次のおすすめを1つだけ伝える。

## 新規レビュー

今のコードに合わせてヒントを全部出し直す。前回の合格チェックが全部合格していなくてもよい。

1. 既存の `HINTS.md` を読み、「チェック履歴」と「合格したヒント」を控えておく。
2. 初回レビューと同じ手順でレビューする。前回の未合格ヒントと同じ問題が今も残っていれば、新しいヒントとして書き直して含めてよい（前回の番号は引き継がず、1から振り直す）。
3. `HINTS.md` を書き直す。「チェック履歴」はそのまま残して末尾に「新規レビュー」の行を足す。前回までの「合格したヒント」は「これまでに合格したヒント」として残す。

## 実行による確認

コンソールで対話するプログラムは、入力をファイルにまとめて標準入力から流し込めば、人が操作しなくても実行できる。

```bash
javac -encoding UTF-8 -d <一時フォルダ> $(find src -name "*.java")
java -cp <一時フォルダ> <メインクラス> < input.txt
```

- コンパイル結果の出力先と `input.txt` は、プロジェクトの外の一時フォルダに置く。学生のプロジェクトにファイルを増やさない。
- 入力が足りずに `NoSuchElementException` で止まるのは、入力の終わりに着いただけのことが多い。バグと区別する。
- 無限ループに備えて、`timeout` などで実行時間を区切る。

## ヒントへの質問

ヒントは段階的に小出しにせず、最初のレビューで「直す手順」まで出しておく。それでもわからないところは、学生が自然言語で質問してくる（例：「ヒント3で、enum を作ったけどどこで状態を変えればいい？」）。

- `HINTS.md` と今のソースを読んで、**チャットで**答える。`HINTS.md` は書き換えない。
- 質問にまっすぐ、2〜6文程度で短く返す。見るべき場所を `ファイル:行` で指す。
- 答えのコードは書かない。必要なら API や書き方を一般形で示す（例：`list.remove(index)`）。目の前のコードを「何行目をこう書き換える」とは言わない。
- 学生の考えが合っていれば、合っていると短く伝える。ずれていれば、どこがずれているかを問いで返す。

## 文章のトーン

- やわらかい です・ます で書く（「〜してみましょう」「〜ですよね」）。上から目線の断定や説教口調は避ける。
- 「もう少し」の判定でも、できている部分を先に認める。
- 見出しは「何をするか」がわかるメッセージにする（例：「ヒント3：延滞しても客は別人にならないので、状態を持たせよう」）。
- `natural-japanese` スキルが使える環境なら、`HINTS.md` を書いたあとにクイックモードで文体チェックをかける。
